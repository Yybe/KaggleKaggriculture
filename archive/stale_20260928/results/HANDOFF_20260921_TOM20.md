## 4. EXACTLY WHERE IT STOPPED, and the one open design question

**Verified working:** champion md5 pin unchanged; builder idempotent; the built
artifact compiles and imports. On seed 7770000 (the only gate seed where V219
fires at all vs `lynnsakurai_v3`) V219 commits at step 433 with
`BUY_LAND + BUY_SEED TOMATO 10 + 2 HIRE + 7 HIRE`.

**TOM20's commit gate was traced 7 times (steps 432-438) and never fired.**

Root cause of the miss, found and evidenced (`results/tom20_dbg15.log`,
`results/tom20_dbg13b.log`, gates dict at the final step shows
`{'day': 18, 'elig': True, 'vcomm': True, 'lock': 0, 'mkt': 0}`):

* step 432: V219 commits this very step, SE is **still LOCKED** (lock=10), and
  the parent already carries **10 market orders** -> TOM20's
  `len(parent)+3 > 10` gate bails. Correct behaviour: V219 is using the whole cap.
* step 433: SE unlock lands (lock=0) but the parent banked `BUY_LAND` +
  `BUY_SEED TOMATO 10` in that same turn, so TOM20 would double-buy land.
* step 434+: V219 is committed and SE is unlocked, but by then V219's own 2
  workers already own the 10 SE cells, so "cells still LOCKED" can never hold
  again. **The window is 1-2 steps wide and fully occupied by V219's own order.**

The current fire rule is therefore (correctly, conservatively) **inert** - a safe
no-op, not a broken agent. It cannot produce the 20th tomato as written. This is
the exact point to pick up from.

**Open design question for the next IDE** (pick one, then gate):

1. **Share V219's order.** Fire in the same turn as V219's commit (432/433) and
   *amend* the parent's own `['BUY_SEED','TOMATO',10]` to 20 and its HIRE count
   by +2 instead of appending orders. Cheapest correct form: intercept
   `_v219_request` (precedent: champion line 6428
   `_V13V_ORIG_REQUEST = _v219_request` already wraps it) so the planner knows it
   owns 20 cells, adjusts `crop_workers`, and updates the V13 skip-day guard
   (which iterates `state['targets']`, 10 entries, and must see 20).
2. **Grow V219's own target list to 20 cells** and re-derive its worker grouping
   for 26<=day<=28 (current grouping is
   `[[(5,5),(6,5),(7,5)],[(8,5),(9,5),(9,6),(8,6)],[(5,6),(6,6),(7,6)]]` = 10
   cells). Honors the E53e/f crew-index law only if headcount stays aligned.
3. **Clean two-block split:** point V219's first block at rows 5-6 and let TOM20
   take rows 7-8 with its own commit - effectively option 2 but with ownership
   separated by row band.

Recommendation: **option 1 or 2** (one planner owning 20 cells). Two co-existing
planners cannot both be "the" V219 and the market cap is 10 orders/turn.

## 6. Operational notes learned the hard way this session

* PowerShell here is `powershell.exe`; `head`/`tail` do not exist, and one command
  call times out at **30 s**. Any engine run longer than that must be launched
  with `Start-Process -FilePath C:\...\WybeV2\rank_env\Scripts\python.exe
  -ArgumentList '<script>','<args>' -WorkingDirectory <root>
  -RedirectStandardOutput <log> -RedirectStandardError <err>`, then polled with a
  separate short command. The redirect log flushes late - poll until
  `Get-Process python` drops before trusting an empty log.
* Bare `python` is a Store stub: use `py` or the `rank_env` interpreter.
* `cmd /c "set PYTHONIOENCODING=utf-8 && ..."` is the reliable way to get CJK
  names printed (PowerShell's `$env:` + redirect worked too but threw on some
  quoting).
* Do **not** rely on `print()` from inside an engine run for verification; read
  module-global telemetry dicts (`_TOM20_ST`, `_V219_REPORT`, `_R85_REPORT`)
  after `env.run(...)` instead. `print` output was dropped in most of the
  `Start-Process` runs here.
* `tools/extract_live_opponents.py` writes ONLY the opponent tape; for our own
  seat use `tools/both_tapes.py <replay.json> <outdir>`.
* One sim of champion vs `lynnsakurai_v3` = ~5-20 s; importing the 1 MB agent
  file costs ~5 s each time.
